# HMI 작화 가능성 검토

작성일: 2026-08-02

## 결론

**가능하다.** 기술적 불확실성이 있는 영역은 없다.
작화 시스템은 이미 확립된 패턴(SVG 씬 그래프 + 태그 바인딩 + 구독 기반 런타임)의
조합이고, 이 저장소의 `prototype/hmi-authoring-poc.html` 로 전체 루프를
동작시켜 확인했다.

다만 **"가능한가"와 "얼마나 드는가"는 다른 질문**이고, 실제 공수는 렌더링이 아니라
편집 UX와 데이터 파이프라인에 몰려 있다. 아래 3~5절이 그 내용이다.

---

## 1. 작화 시스템의 구성

작화 도구는 항상 세 층으로 나뉜다. 층별로 난이도가 크게 다르다.

| 층 | 역할 | 난이도 | 비고 |
|---|---|---|---|
| **에디터** | 심볼 배치·이동·정렬·속성 편집 | 중~상 | 공수의 대부분이 여기 |
| **저장 포맷** | 화면 = 데이터. 직렬화/버전 관리 | 하 | 설계만 제대로 하면 끝 |
| **런타임 뷰어** | 실 데이터로 심볼 애니메이션 | 중 | 성능·연동이 관건 |

핵심은 **화면을 코드가 아니라 데이터로 다루는 것**이다. PoC의 저장 포맷은 이렇다.

```json
{
  "version": 1,
  "width": 1100, "height": 680,
  "nodes": [
    { "id": "n5", "type": "fan", "x": 340, "y": 118, "w": 76, "h": 76,
      "tag": "AHU1_SF_RUN", "mode": "rotate" },
    { "id": "n14", "type": "tank", "x": 180, "y": 380, "w": 90, "h": 120,
      "tag": "TANK1_LEVEL", "mode": "level" }
  ]
}
```

한 노드는 **무엇을(type) / 어디에(x,y,w,h) / 어떤 포인트에 묶여(tag) / 어떻게 반응하나(mode)**
네 가지만 갖는다. 이 구조가 잡히면 나머지는 전부 부수적이다.
포인트 리스트로부터 화면을 자동 생성하거나, 화면 수백 장을 일괄 수정하는 것도
결국 이 JSON을 다루는 문제가 된다.

## 2. PoC로 확인한 것

`prototype/hmi-authoring-poc.html` — 의존성 없는 단일 HTML. 브라우저로 열면 바로 동작.
헤드리스 Chromium으로 검증 완료(JS 오류 0).

- 심볼 팔레트 9종: 탱크 / 펌프 / 팬 / 밸브 / 댐퍼 / 표시등 / 수치 / 배관 / 텍스트
- 클릭 배치, 드래그 이동(10px 스냅), 선택, Delete 삭제
- 속성 패널에서 **포인트 태그 ↔ 심볼 바인딩**, 애니메이션 방식 선택
- 애니메이션 5종: 정적 / 색 변화(bool) / 회전(bool) / 레벨·개도(0~100) / 값 표시
- 편집 ↔ 런타임 모드 전환, 런타임에서 모의 데이터로 실시간 갱신
- JSON 저장·불러오기 라운드트립
- AHU 계통도 샘플 21개 심볼

즉 **작화 → 저장 → 런타임 구동**이라는 전체 루프가 이미 돈다.

### 검증하지 않은 것 (의도적으로 범위 밖)

실 장비 연동, 다중 화면/네비게이션, 권한, 알람 확인(ack), 트렌드 차트,
되돌리기(undo), 그룹·정렬 도구, 인쇄. 전부 "어려워서"가 아니라 분량 때문에 뺐다.

## 3. 진짜 공수가 드는 곳

가능성 판단에서 자주 과소평가되는 부분이다. 렌더링은 쉽고, 아래가 어렵다.

**① 편집 UX (전체 공수의 50~60%)**
스냅·가이드, 다중 선택, 정렬/균등 배치, z-order, 그룹화, 되돌리기/다시하기,
복사·붙여넣기, 확대·축소·패닝. 하나하나는 사소한데 안 만들면 현장에서 "못 쓰겠다"는
말이 나오고, 다 만들면 상당한 분량이 된다. 되돌리기는 특히 씬 모델을 처음부터
불변(immutable) 스냅샷 구조로 잡아두지 않으면 나중에 넣기가 매우 번거롭다.

**② 데이터 파이프라인**
심볼에 값을 흘려넣는 부분. 폴링이 아니라 **구독(subscribe)** 으로 가야 한다.
화면당 포인트 200~500개, 갱신 1초 주기를 기준으로 잡으면
- 장치 측: Sedona SOX는 포인트 구독을 지원하므로 이걸 그대로 쓰고,
  브리지가 SOX ↔ WebSocket 변환을 맡는다 (포트 5001 — 80은 장치 웹서버 전용).
- 브리지 측: 변경분만 push. 전체 스냅샷을 매 틱 보내면 곧 한계가 온다.
- 화면 전환 시 구독 해제/재등록을 반드시 처리. 이걸 빠뜨리면 몇 시간 켜둔 뒤
  브리지가 죽는다. 실제로 가장 흔한 사고 지점이다.

**③ 심볼 라이브러리**
AHU, 냉동기, 보일러, 열교환기, 펌프, 각종 밸브·댐퍼... 현장에서 요구하는 심볼은
계속 늘어난다. 어렵진 않고 순수 물량이다. **완화책**: 심볼을 코드가 아니라
SVG 파일로 정의하고 `data-part` 속성으로 애니메이션 훅을 표시하게 하면,
디자이너가 Inkscape/Illustrator로 그린 걸 그대로 쓸 수 있어 개발자 손을 탈 필요가 없다.
PoC는 코드로 그렸지만 이 방식으로 바꾸는 건 어렵지 않다.

**④ 성능**
SVG 노드가 수천 개를 넘으면 브라우저가 느려진다. 화면 한 장에 심볼 수백 개 수준이면
SVG로 충분하고, 그 이상(전체 계통도, 대형 평면도)은 Canvas 렌더링을 검토해야 한다.
현실적으로는 화면을 쪼개는 쪽이 먼저다.

**⑤ 태그 네임스페이스 안정성**
포인트 이름/주소가 바뀌면 화면이 통째로 깨진다. 심볼은 이름이 아니라
**안정적인 ID**에 묶고, 이름은 표시용으로만 쓰는 게 안전하다.
장비 교체·재설치 후에도 바인딩이 살아남아야 한다.

## 4. 웹 vs 데스크톱

| | 웹 (SVG + JS) | PyQt6 (QGraphicsScene) |
|---|---|---|
| 런타임 배포 | 브라우저만 있으면 됨 | 클라이언트 설치 필요 |
| 모바일·태블릿 | 그대로 됨 | 사실상 불가 |
| 편집기 완성도 | 직접 다 만들어야 함 | Qt가 상당 부분 제공 |
| 기존 자산 | — | NeoBAS 캔버스/와이어링 재사용 가능 |

**권장: 런타임은 웹, 편집기는 상황에 따라.**
런타임 뷰어를 웹으로 두면 현장 태블릿까지 한 번에 커버된다.
편집기는 NeoBAS App Editor가 이미 QGraphicsScene 기반 캔버스와 선택/드래그/
와이어링을 갖고 있으므로, 블록 다이어그램 에디터와 작화 에디터는 씬 그래프
관점에서 거의 같은 문제다 — 재사용 여지가 크다.
다만 편집기와 뷰어를 서로 다른 스택으로 가져가면 **심볼을 두 번 구현**해야 하므로,
심볼을 SVG 파일로 정의해 양쪽이 공유하는 구조가 전제되어야 한다.
그게 부담되면 편집기도 웹으로 통일하는 편이 단순하다.

## 5. 단계별 계획

거친 추정이며, 요구사항 상세화에 따라 크게 흔들릴 수 있다.

| 단계 | 내용 | 대략 |
|---|---|---|
| 1 | 씬 포맷 확정 + 런타임 뷰어 (읽기 전용, 실 데이터 연동) | 2~3주 |
| 2 | SOX ↔ WebSocket 브리지, 구독·재연결·화면전환 처리 | 2~3주 |
| 3 | 편집기 기본 (배치·이동·속성·저장) | 3~4주 |
| 4 | 편집 UX 완성 (undo, 그룹, 정렬, 줌) | 3~4주 |
| 5 | 심볼 라이브러리 + 알람/트렌드 연계 | 지속 |

**1단계를 먼저** 하는 것을 권한다. 화면은 손으로 JSON을 써서라도 만들 수 있지만,
실 데이터가 안 붙으면 편집기를 아무리 잘 만들어도 쓸모가 없다.
가장 위험한 구간(② 데이터 파이프라인)을 앞에 배치하는 순서이기도 하다.

## 6. 다음 단계

이 문서는 **일반적인 HMI 작화 가능성**만 다룬다.
GreenSCADA에 실제로 얹는 판단을 하려면 다음이 필요하다.

- GreenSCADA 소스 위치 (저장소명 또는 압축 파일) — 현재 이 세션에서는 접근 불가
- 기존 화면/프로젝트 파일 포맷 — 이미 저장 포맷이 있다면 그걸 따르는 게 맞다
- 대상 장비와 통신 경로 (EasyIO/Sedona SOX인지, BACnet/Modbus인지)
- 화면 규모: 총 화면 수, 화면당 포인트 수, 갱신 주기 요구

이 네 가지가 확인되면 위 추정을 실제 계획으로 좁힐 수 있다.
