# 로컬 AI 기반 작화 자동 생성

작성일: 2026-08-02

## 결론

**가능하다. 단, LLM을 분류기 자리에만 넣어야 한다.**

작화 자동 생성을 통째로 LLM에 맡기면 실패한다. 좌표를 LLM이 정하면
같은 입력에도 매번 다른 화면이 나오고 심볼이 겹친다. 역할을 이렇게 나눈다.

```
포인트 리스트
    │
    ├─ [LLM]  태그 이름 해석 → 장비/역할 분류    ← 애매하고 사람 말에 가까운 일
    │
    ├─ [규칙]  역할 → 심볼·애니메이션 매핑       ← 표 한 장
    │
    └─ [코드]  템플릿 배치 → 좌표 계산           ← 결정론적이어야 하는 일
                                                    ↓
                                                화면 JSON
```

LLM이 맡는 구간은 전체의 일부지만, **딱 그 구간이 규칙으로는 안 되는 부분**이다.

구현: `tools/gen_screen.py` · 샘플 입력: `tools/sample_points.csv`

```bash
python3 tools/gen_screen.py tools/sample_points.csv -o screens/          # 규칙 기반
python3 tools/gen_screen.py tools/sample_points.csv -o screens/ --llm    # 로컬 LLM
```

## 왜 좌표를 LLM에 시키면 안 되는가

- **재현성이 없다.** 같은 포인트 리스트로 어제와 오늘 화면이 다르면 검수가 불가능하다.
- **겹친다.** 모델은 심볼 크기와 라벨 길이를 정확히 계산하지 못한다.
- **검증이 안 된다.** 코드로 배치하면 "겹침 0개, 화면 밖 0개"를 자동 검사할 수 있다.
  실제로 이 프로젝트에서 그 검사가 라벨 겹침 버그와 블록 침범 버그를 잡아냈다.
- **고칠 수가 없다.** 배치가 마음에 안 들면 템플릿 상수 하나 바꾸면 되는데,
  LLM이 그렸으면 프롬프트를 붙잡고 씨름해야 한다.

배치는 코드가 훨씬 잘하는 일이다. 굳이 넘길 이유가 없다.

## LLM이 실제로 필요한 지점

규칙 기반 분류기(정규식)로 대부분 처리되지만, **표기 흔들림**에서 무너진다.
샘플에서 실제로 나온 사례:

| 태그 | 규칙 기반 | 실제 의미 |
|---|---|---|
| `펌프1 운전` | 장비 `펌프-1` | `PUMP-1` 과 같은 장비 |
| `PUMP-1 압력` | 장비 `PUMP-1` | 위와 같은 장비인데 따로 잡힘 |

한글/영문 혼용, 약어 불일치, 현장마다 다른 명명 규칙 — 정규식으로 덮으려면
현장마다 규칙을 새로 짜야 한다. **이걸 흡수하는 게 LLM을 쓰는 유일한 이유이자
충분한 이유다.** 스텁 서버로 확인한 결과 `펌프1 운전`과 `PUMP-1 압력`이
`PUMP-1` 하나로 병합됐다.

## 모델과 하드웨어

분류만 시키므로 **큰 모델이 필요 없다.**

| 항목 | 권장 |
|---|---|
| 모델 크기 | 7~14B급 코더/인스트럭트 (예: Qwen2.5-Coder 7B/14B) |
| VRAM | 7B Q4 ≈ 6GB, 14B Q4 ≈ 10GB — 일반 게이밍 GPU로 충분 |
| temperature | **0**. 분류는 창의성이 필요 없고 재현성이 필요하다 |
| 출력 | **구조화 출력(JSON 스키마) 필수**. 자유 텍스트를 파싱하면 반드시 깨진다 |
| 배치 크기 | 20~30개씩. 한 번에 다 넣으면 컨텍스트가 길어져 품질이 떨어진다 |

`OllamaClassifier` 는 Ollama의 `/api/chat` 에 `format` 으로 JSON 스키마를 넘겨
출력 형식을 강제한다. 서버가 다른 것(llama.cpp 등)이어도 스키마 강제 기능만
있으면 클래스 하나만 갈아끼우면 된다.

## 반드시 넣어야 하는 것: 폴백

**LLM이 죽어도 파이프라인은 돌아야 한다.** `OllamaClassifier` 는

1. 먼저 규칙 기반으로 전부 채워 기본값을 확보하고,
2. LLM 응답이 온 항목만 덮어쓰며,
3. 서버가 죽었거나 응답이 스키마에 안 맞으면 조용히 규칙 기반 결과를 쓴다.

검증 결과:

```
=== LLM 정상 ===        LLM 분류 29개 / 폴백 0개    → 화면 2장
=== 서버 다운 ===       LLM 분류 0개 / 폴백 29개    → 화면 2장 (정상 생성)
```

응답에 없는 태그나 정의되지 않은 역할이 섞여 와도 무시된다.
로컬 모델은 클라우드보다 이런 오염된 출력이 잦으므로 이 방어가 특히 중요하다.

## 검증 결과

샘플 29개 포인트(한글/영문 혼용, 표기 불일치 포함) 기준:

- 장비 8개 자동 인식 → 화면 2장 생성, 심볼 66개
- 브라우저 렌더 후 **심볼 겹침 0건, 화면 밖 이탈 0건**
- 생성 JSON을 `prototype/hmi-authoring-poc.html` 에서 그대로 열어 런타임 동작 확인

개발 중 이 자동 검사가 잡아낸 실제 버그:

1. `AHU1_SF_RUN` 형태가 장비 인식에서 전부 누락 — 정규식의 `\b`가
   숫자와 언더스코어 사이에서 성립하지 않음
2. 라벨끼리 가로로 겹침 — 슬롯 폭을 심볼 폭만으로 잡아서
3. 포인트 많은 장비의 표시등 목록이 아래 블록 침범 — 블록 높이 고정 때문
4. `팬 트립` → 경보가 아니라 팬으로 분류 (영문 `TRIP`만 있고 한글 `트립` 누락)
5. `PUMP-1 압력` → 수치가 아니라 펌프 심볼로 분류 (장비 패턴이 먼저 걸림)

**자동 생성에는 자동 검사가 반드시 따라와야 한다**는 근거다.
사람이 눈으로 보는 검수는 화면이 수십 장 넘어가면 무너진다.

## 한계 — 자동 생성은 초안이다

자동 생성이 만들어주는 것은 **심볼 배치와 데이터 바인딩까지**다.
아래는 여전히 사람 몫이다.

- **계통 연결선/배관** — 장비 간 흐름 관계는 포인트 리스트에 없는 정보다.
  도면이나 시퀀스를 봐야 알 수 있다.
- **평면도 위 배치** — 실제 위치 정보가 필요하다.
- **화면 구성 의도** — 무엇을 크게 볼지, 무엇을 한 화면에 묶을지.

현실적인 기대치는 **"백지에서 시작하지 않게 해주는 것"** 이다.
포인트 300개짜리 현장에서 심볼 배치와 태그 바인딩이 이미 끝난 초안이 나오면,
작화 공수의 상당 부분이 줄어든다. 여기서 사람이 배관 긋고 배치를 다듬는다.

   태그 명명이 일관된 현장이면 규칙만으로 충분할 수 있다.
2. 로컬 LLM을 실제로 띄워 분류 정확도 비교 (현재는 스텁으로 코드 경로만 검증).
3. 템플릿 확장 — 현재는 AHU형 흐름도 하나. 냉동기·보일러·펌프군 템플릿 추가.
4. GreenSCADA 화면 포맷이 확인되면 출력부만 교체. 파이프라인 나머지는 그대로 쓴다.
